# PartyCRM Payout Status From Transactions Design

## Context

В заказе PartyCRM у каждого назначенного исполнителя есть плановый `payoutAmount` и ручной `payoutStatus`. При этом фактические оплаты уже ведутся через транзакции заказа, где расход с категорией `payout` означает выплату исполнителю. Ручной статус создаёт второй источник правды и может расходиться с реальными расходными операциями.

## Decision

`payoutAmount` остаётся плановой суммой выплаты конкретному исполнителю. `payoutStatus` перестаёт редактироваться вручную в редакторе заказа и показывается как производный текстовый статус.

Производный статус считается по сумме расходных транзакций заказа с категорией `payout`, привязанных к конкретному `staffId`:

- `none` — плановый гонорар равен 0.
- `unpaid` — гонорар больше 0, привязанных payout-транзакций нет.
- `partial` — сумма payout-транзакций больше 0, но меньше гонорара.
- `paid` — сумма payout-транзакций больше или равна гонорару.

Для новых payout-транзакций выбор исполнителя обязателен. Для остальных категорий `staffId` не используется.

## Compatibility

Старое поле `assignedStaff[].payoutStatus` остаётся в схеме и API как legacy fallback для старых данных и внешних клиентов, но UI больше не даёт редактировать его напрямую. Основные проверки, фильтры, сводки и статус команды должны использовать вычисление по транзакциям.

## Affected Areas

- Схема `PartyTransaction`: добавить опциональный `staffId`.
- Серверная нормализация транзакций: принимать и сериализовать `staffId`.
- API транзакций: требовать `staffId` для `expense + payout` и проверять, что исполнитель назначен на этот заказ.
- Финансовые helper'ы: считать статусы выплат по `assignedStaff` и `transactions`.
- Редактор заказа: заменить select `Статус выплаты` на read-only текст.
- Форма транзакции: при `Расход -> Выплата исполнителю` показать обязательный выбор исполнителя.

## Testing

Проверки должны покрыть:

- расчёт статуса `none`, `unpaid`, `partial`, `paid` по сумме payout-транзакций конкретного исполнителя;
- отсутствие зачёта payout-транзакций другого исполнителя;
- нормализацию/сериализацию `staffId`;
- source-тесты API на обязательную проверку `staffId` для payout;
- source-тесты UI на отсутствие ручного select статуса и наличие выбора исполнителя в payout-транзакции.
