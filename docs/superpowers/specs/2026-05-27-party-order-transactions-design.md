# Дизайн транзакций заказа в PartyCRM

**Дата:** 2026-05-27

## Цель

Убрать из формы создания и редактирования заказа `PartyCRM` ручные поля `Предоплата` и `Статус оплаты` и перевести финансовую модель заказа на отдельные транзакции по образцу `ArtistCRM`.

Цель не в косметической замене полей, а в том, чтобы заказ перестал хранить две параллельные финансовые модели:

- legacy `clientPayment` и вложенный `order.transactions`;
- новая каноническая модель через отдельную коллекцию `Transactions`.

## Текущий контекст

### PartyCRM

- Форма заказа находится в [components/party/modals/OrderModal.js](/d:/Programming/Projects/ArtistCRM_PartyCRM/PartyCRM/components/party/modals/OrderModal.js).
- API создания заказа сейчас принимает:
  - `contractAmount`;
  - `clientPayment.totalAmount`;
  - `clientPayment.prepaidAmount`;
  - `clientPayment.status`;
  - вложенный массив `transactions`.
- Нормализация запроса находится в [app/api/party/orders/route.js](/d:/Programming/Projects/ArtistCRM_PartyCRM/PartyCRM/app/api/party/orders/route.js).
- В модели заказа уже есть поле `transactions`, но оно не должно оставаться основным источником правды.

### ArtistCRM

- Модалка события уже использует полноценный блок транзакций в [layouts/modals/modalsFunc/eventFunc.js](/d:/Programming/Projects/ArtistCRM_PartyCRM/ArtistCRM/layouts/modals/modalsFunc/eventFunc.js).
- Транзакции живут в отдельной коллекции `Transactions`, грузятся через `useTransactionsQuery`, а создание/редактирование/удаление вынесено в отдельные mutation-хуки.
- Производные признаки вроде “есть задаток” и “что показывать в финансах” вычисляются по транзакциям, а не по отдельным ручным флагам.

## Проблема текущей модели

- `Предоплата` и `Статус оплаты` в форме заказа дублируют смысл транзакций.
- Пользователь может заполнить `prepaidAmount`, но не создать фактическое поступление денег.
- `paymentStatus` становится ручным флагом, который может расходиться с реальными поступлениями.
- API заказа уже умеет принимать `transactions`, но UI заказа не построен вокруг них как вокруг основной финансовой сущности.

В результате система хранит финансовую правду в двух местах, а это архитектурно неверно.

## Целевая модель

### 1. Канонический источник правды

Каноническая финансовая модель заказа в `PartyCRM` должна быть такой же, как в `ArtistCRM`:

- каждая денежная операция — отдельная транзакция;
- транзакции живут в отдельной коллекции `Transactions`;
- заказ связан с транзакциями по `orderId`;
- UI заказа показывает агрегаты и статусы, вычисленные из списка транзакций.

### 2. Что убирается из UI

Из формы заказа убираются поля:

- `Предоплата`;
- `Статус оплаты`.

Поле `Сумма клиента` может остаться как договорная сумма/ожидаемая выручка, потому что это не транзакция, а финансовый ориентир заказа.

### 3. Что добавляется в UI

В `OrderModal` появляется полноценный блок `Транзакции`, аналогичный `ArtistCRM`:

- список поступлений;
- список расходов;
- кнопка `Добавить транзакцию`;
- редактирование транзакции;
- удаление транзакции;
- производные подсказки и статусы на основе уже сохранённых транзакций.

### 4. Поведение для нового заказа

Для нового, ещё не сохранённого заказа блок транзакций не должен создавать транзакции “в никуда”.

Ожидаемое поведение:

- если заказ ещё не сохранён, нажатие `Добавить транзакцию` сначала вызывает автосохранение заказа;
- после успешного сохранения открывается форма транзакции, уже привязанная к `orderId`;
- если обязательные поля заказа не заполнены и автосохранение невозможно, пользователю показывается понятная ошибка.

Это поведение должно повторять рабочую идею `ArtistCRM`.

## Архитектурное решение

### 1. Отдельный party-specific слой транзакций

Нужно сделать party-specific CRUD для транзакций заказа, а не использовать legacy `/api/transactions` из `ArtistCRM` напрямую.

Причины:

- `PartyCRM` живёт на app-router и party-auth;
- party-API обязано проверять `tenantId` и активную компанию;
- транзакции заказа должны проверять принадлежность `orderId` к активной компании.

### 2. Совместимость на переходе

Новые записи должны создаваться только как отдельные транзакции.

Legacy-поля:

- `clientPayment`;
- `order.transactions`;

нужны только как временный compatibility-layer.

Допустимая стратегия перехода:

- в новой UI они больше не редактируются;
- на чтении можно временно поддержать fallback, если у старого заказа ещё нет отдельных транзакций;
- после миграции их можно будет удалить отдельной задачей.

### 3. Производная бизнес-логика

После перехода следующие признаки должны вычисляться по транзакциям:

- есть ли задаток;
- полностью ли оплачен заказ;
- сколько фактически получено от клиента;
- есть ли расходы по заказу;
- какие действия доступны в финансовом блоке.

Ручное редактирование `paymentStatus` больше не допускается.

## Границы задачи

Входит:

- убрать `Предоплата` и `Статус оплаты` из формы заказа;
- добавить в `OrderModal` полноценный блок транзакций;
- сделать party-specific query/mutation/API для транзакций заказа;
- перевести финансовую логику заказа на отдельную коллекцию `Transactions`;
- защитить сценарий нового заказа через автосохранение перед добавлением транзакции;
- предусмотреть миграционный compatibility-layer для существующих данных.

Не входит:

- полная ликвидация всех legacy financial fields во всём коде в один шаг;
- массовая офлайн-миграция старых заказов без отдельного миграционного плана;
- переделка общей финансовой аналитики PartyCRM, не связанной с заказом.

## Риски

- В `PartyCRM` уже есть вложенный `order.transactions`, поэтому легко случайно оставить два источника правды.
- Без route/API-изоляции можно непреднамеренно подтянуть legacy ArtistCRM endpoints.
- Автосохранение перед созданием транзакции может дать регрессию в UX, если не будет чётко обработан сценарий ошибок валидации.

## Принятые решения

- `PartyCRM` идёт по модели `ArtistCRM`: отдельная коллекция `Transactions` и полноценный inline-блок транзакций в заказе.
- `Предоплата` и `Статус оплаты` удаляются из `OrderModal`.
- `Сумма клиента` остаётся как договорная сумма заказа.
- Ограничение на новый заказ решается через автосохранение перед открытием формы транзакции.
- Legacy `clientPayment` и `order.transactions` считаются временной совместимостью, а не канонической моделью.
