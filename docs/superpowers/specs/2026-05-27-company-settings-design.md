# Дизайн раздела "Настройки компании" в PartyCRM

**Дата:** 2026-05-27

## Цель

Добавить в кабинет компании `PartyCRM` новый раздел `Настройки компании` в сайдбаре и реализовать в нем тот же набор подпунктов, что уже существует в `ArtistCRM`: `Общие`, `Интеграции`, `Списки`, `Уведомления`, `Документы`, `Тарифы`.

Цель не в механическом копировании UI из `ArtistCRM`, а в переносе структуры раздела и функциональных возможностей на модель компании `PartyCRM`, где источником данных выступает `PartyCompanies.settings` и связанные party-API.

## Текущий контекст

### PartyCRM

- Основной сайдбар компании описан в `components/party/PartyAppShell.js`.
- Основные рабочие разделы компании отрисовываются через `app/company/[section]/page.js` и `app/company/CompanyWorkspaceClient.js`.
- Настройки компании уже частично существуют в модели данных:
  - `app/api/party/company-settings/route.js`
  - `schemas/partyCompaniesSchema.js`
- Сейчас `companySettings` используются точечно, например в `OrderModal` для адресов и городов.

### ArtistCRM

- Структура разделов настроек разбита по отдельным content-блокам:
  - `layouts/content/SettingsContent.js`
  - `layouts/content/IntegrationsContent.js`
  - `layouts/content/ListsContent.js`
  - `layouts/content/NotificationsContent.js`
  - `layouts/content/DocumentsContent.js`
  - `layouts/content/TariffsContent.js`
- Это хороший ориентир по составу страниц, но не по архитектуре: `PartyCRM` уже использует app-router и явные роуты, поэтому та же идея должна быть реализована через отдельную ветку маршрутов.

## Границы задачи

В рамках дизайна раздел `Настройки компании` считается отдельным модулем внутри company workspace.

В задачу входит:

- добавить новый entry-point в сайдбар компании;
- сделать отдельную ветку роутов `app/company/settings/*`;
- реализовать внутреннее подменю настроек;
- подготовить страницы под все 6 подпунктов;
- адаптировать источники данных и сохранение под `PartyCompanies.settings`;
- переиспользовать существующие компоненты `PartyCRM` и бизнес-логику там, где это возможно;
- заложить расширяемую архитектуру, чтобы настройки не разрастались внутри `CompanyWorkspaceClient`.

В задачу не входит:

- перенос legacy-архитектуры `ArtistCRM` в `PartyCRM`;
- смешивание company settings с личными настройками `/party/settings`;
- внедрение настроек компании внутрь `CompanyWorkspaceClient` как еще одной giant-section;
- реализация несвязанных изменений в operational UI компании.

## Рекомендуемая архитектура

### 1. Новая ветка роутов

Нужна отдельная ветка:

- `app/company/settings/page.js`
- `app/company/settings/[tab]/page.js`
- `app/company/settings/layout.js`

Где:

- `/company/settings` открывает дефолтный подпункт `Общие`;
- `/company/settings/[tab]` обслуживает конкретную вкладку;
- layout использует `PartyAppShell` c отдельным variant для company settings.

Это лучше, чем:

- держать все на одном route с hash;
- встраивать новые секции в `CompanyWorkspaceClient`;
- пытаться переиспользовать старую систему content-map из `ArtistCRM`.

### 2. Отдельный shell для настроек компании

Нужен самостоятельный client-shell, например уровня:

- `app/company/settings/CompanySettingsShell.js`
- `app/company/settings/companySettingsTabs.js`

Его ответственность:

- проверить текущую активную компанию;
- загрузить `companySettings`;
- отрисовать локальную навигацию по подпунктам;
- передать данные в конкретный content component;
- централизовать сохранение patch-обновлений.

Это разгрузит `CompanyWorkspaceClient`, который уже перегружен CRUD-логикой заказов, клиентов, сотрудников и точек.

### 3. Отдельные content-компоненты

Для каждого подпункта должен быть собственный компонент с узкой ответственностью:

- `CompanySettingsGeneralContent`
- `CompanySettingsIntegrationsContent`
- `CompanySettingsListsContent`
- `CompanySettingsNotificationsContent`
- `CompanySettingsDocumentsContent`
- `CompanySettingsTariffsContent`

Компоненты должны жить рядом с модулем настроек компании, а не внутри общего operational workspace.

## Структура навигации

### Глобальный сайдбар

В `components/party/PartyAppShell.js` добавляется новый пункт верхнего уровня:

- `Настройки компании` -> `/company/settings`

Он должен быть виден в company-variant и логически стоять рядом с разделами компании, а не смешиваться с персональным `/party/settings`.

### Локальное меню настроек

Внутри `/company/settings/*` нужно отдельное меню подпунктов:

- `Общие`
- `Интеграции`
- `Списки`
- `Уведомления`
- `Документы`
- `Тарифы`

Ожидаемые URL:

- `/company/settings`
- `/company/settings/integrations`
- `/company/settings/lists`
- `/company/settings/notifications`
- `/company/settings/documents`
- `/company/settings/tariffs`

Маршрут `/company/settings` должен резолвиться в `Общие`, без дублирования страницы в двух местах.

## Модель данных

### Базовый источник

Основной источник настроек компании:

- `PartyCompanies.settings`

Текущий API `app/api/party/company-settings/route.js` уже умеет:

- читать `settings`;
- сохранять patch для `towns` и `addresses`.

Его нужно расширить до централизованной точки сохранения company settings для большинства подпунктов.

### Принцип хранения

Новые настройки компании должны сохраняться в `settings` по плоским и предсказуемым ключам или в небольших логических вложенностях, а не в бесконтрольной legacy-свалке.

Предпочтительная структура:

- top-level поля для простых company settings;
- вложенные объекты для изолированных подсистем;
- массивы только там, где пользователь редактирует списки сущностей.

Пример групп:

- `settings.timeZone`
- `settings.defaultOrderDurationMinutes`
- `settings.towns`
- `settings.addresses`
- `settings.eventTypes`
- `settings.notifications`
- `settings.documents`
- `settings.integrations`

Точная схема фиксируется на этапе implementation plan по каждой вкладке.

## Дизайн подпунктов

### 1. Общие

Назначение:

- базовые настройки компании, влияющие на поведение кабинета и заказов.

Первый обязательный состав:

- часовой пояс компании;
- стандартная длительность заказа по умолчанию;
- потенциально другие company-level toggles, если они уже есть в `PartyCRM` или нужны для parity с `ArtistCRM`.

Источники:

- новая часть `companySettings`, а не `siteSettingsAtom`.

Принцип:

- если настройка в `ArtistCRM` относится к личному кабинету пользователя, а не к компании, она не переносится сюда один-в-один;
- если настройка влияет на компанию и ее данные, она становится частью company settings.

### 2. Интеграции

Назначение:

- все интеграции компании в одном месте по аналогии с `ArtistCRM`.

Базовый состав для проектирования:

- Google Calendar;
- Avito;
- VK;
- Novofon;
- AITunnel / AI-related keys;
- другие company-integrations, если уже есть party-ready backend.

Ключевой архитектурный вопрос:

- в `ArtistCRM` часть интеграций привязана к user/site-settings;
- в `PartyCRM` их нужно явно классифицировать как company-level или user-level.

Правило:

- если интеграция влияет на работу компании, заказы, общие webhook-и и общие источники лидов, она хранится на уровне компании;
- если интеграция персональная и относится к конкретному исполнителю или личному кабинету, она не должна жить в `Настройках компании`.

Следствие:

- вкладка `Интеграции` потребует отдельной инвентаризации существующих party backend endpoints;
- часть UI можно переиспользовать из `ArtistCRM`, но не переносить без адаптации модели хранения и API.

### 3. Списки

Назначение:

- редактируемые справочники компании.

Обязательный стартовый состав:

- `Города`
- `Типы мероприятий` или аналогичный справочник, если он действительно нужен для party-заказов

Что уже есть:

- `towns` и `addresses` частично поддержаны в company settings;
- логика списков в `ArtistCRM` уже оформлена как отдельный экран и модалки.

Решение:

- `Списки` в `PartyCRM` не должны зависеть от `siteSettingsAtom`;
- редактирование идет через `companySettings` и party API;
- если модалки из `ArtistCRM` сильно завязаны на глобальный app-state, лучше вынести reusable редакторы в отдельные controlled-компоненты.

### 4. Уведомления

Назначение:

- управление push- и связанными уведомлениями для компании.

Текущее состояние:

- в `PartyCRM` уже есть `components/PushNotificationsSettings.js`, но он завязан на `siteSettingsAtom`.

Решение:

- определить, какие именно уведомления должны быть company-level;
- либо адаптировать существующий компонент под controlled-props;
- либо сделать party-specific wrapper над ним.

Ограничение:

- нельзя напрямую использовать user/site-settings storage для company-уведомлений.

### 5. Документы

Назначение:

- шаблоны и настройки документов компании.

Ожидание:

- раздел проектируется как полноценная вкладка, даже если часть возможностей будет реализована поэтапно;
- хранение пользовательских шаблонов и company-реквизитов должно быть привязано к компании.

Это особенно важно для `PartyCRM`, где документы логически связаны с заказами компании, а не с личным кабинетом пользователя.

### 6. Тарифы

Назначение:

- настройки и информация по тарифу компании.

Текущее состояние:

- в `PartyCRM` уже есть отдельные экраны и API вокруг party tariffs.

Решение:

- вкладка `Тарифы` внутри company settings должна стать точкой входа в уже существующий тарифный функционал;
- по возможности использовать текущие party billing / tariffs компоненты, а не дублировать их;
- если текущая тарифная страница достаточно самостоятельна, допускается встроить ее как content-section или сделать адаптер.

## API-стратегия

### Централизованный settings API

Нужен единый API для company settings patch-операций:

- `GET /api/party/company-settings`
- `PATCH /api/party/company-settings`

Требования к `PATCH`:

- принимать частичный patch;
- валидировать только разрешенные ключи;
- сохранять merge-поведение;
- не ломать уже существующие `towns` и `addresses`;
- иметь нормализаторы для массивов, строк, вложенных объектов.

### Специализированные API

Для сложных подсистем допустимы специализированные endpoints, если этого требует интеграция:

- `/api/party/integrations/...`
- `/api/party/documents/...`
- `/api/party/billing/...`

Но экран настроек компании должен оставаться единым UI-level entry point.

## Переиспользование существующего кода

### Что можно переиспользовать почти напрямую

- визуальные паттерны `PartyCRM`;
- party shell и routing conventions;
- существующий `company-settings` API как точку старта;
- существующие billing/tariff screens;
- существующие small UI components (`Input`, `IconCheckBox`, карточки, surface-блоки).

### Что нужно адаптировать

- `ArtistCRM` content screens из настроек;
- компоненты, завязанные на `siteSettingsAtom`;
- компоненты, использующие `postData('/api/site')`;
- интеграции, которые сейчас хранятся на user/site уровне.

### Что не нужно копировать

- content-map navigation из `ArtistCRM`;
- глобальные зависимости на старые модалки и legacy state только ради parity;
- любые user-specific настройки в company-level UI.

## Поведение доступа

Раздел `Настройки компании` должен быть доступен только пользователям компании с management-level доступом:

- `owner`
- `admin`

Для сотрудников без права управления:

- пункт не показывается в сайдбаре, либо
- доступ по URL отсекается на уровне route/layout/API.

Проверка должна быть на обоих уровнях:

- UI;
- server-side route guard.

## Ошибки и состояния

Каждая вкладка должна поддерживать:

- `loading`;
- `empty`, если данных еще нет;
- `saving`;
- `error`;
- success feedback после сохранения.

Не допускается silently-fail поведение, особенно для интеграций и документов.

## Тестовая стратегия

### Unit / logic

Нужны тесты на:

- нормализацию patch-данных company settings;
- merge-логику `PATCH /api/party/company-settings`;
- route-to-tab resolution;
- guards доступа к разделу.

### Integration / UI

Нужны проверки:

- пункт `Настройки компании` виден только там, где должен;
- `/company/settings` открывает дефолтную вкладку;
- переключение между подпунктами работает;
- сохранение настроек отражается после перезагрузки;
- уже существующие сценарии `OrderModal`, использующие `companySettings`, не ломаются.

### Regression focus

Основной риск:

- смешение company settings и personal settings;
- случайный перенос логики на `siteSettingsAtom`;
- разрастание `CompanyWorkspaceClient` вместо выделения нового модуля;
- повреждение существующего формата `settings.addresses` и `settings.towns`.

## Пошаговая реализация на высоком уровне

1. Добавить routing и shell для `Настроек компании`.
2. Добавить глобальный пункт в сайдбар компании.
3. Вынести конфиг вкладок и локальное меню настроек.
4. Реализовать страницу `Общие` на company settings.
5. Реализовать страницу `Списки`, начиная с городов и связанных справочников.
6. Подключить `Тарифы` через уже существующий party billing/tariff функционал.
7. Реализовать `Уведомления` через company-aware storage.
8. Реализовать `Документы` через company-level document settings.
9. Реализовать `Интеграции` после инвентаризации company-ready backend endpoints.
10. Прогнать регрессии по company workspace и settings API.

## Решения, принятые заранее

- Используем отдельную ветку роутов `/company/settings/*`.
- Не добавляем новые секции в `CompanyWorkspaceClient`.
- Делаем тот же набор подпунктов, что и в `ArtistCRM`.
- Источником данных для company settings является `PartyCompanies.settings`, а не `siteSettingsAtom`.
- Личные настройки `/party/settings` остаются отдельным разделом и не смешиваются с company settings.

## Открытые моменты для implementation plan

Эти вопросы не блокируют дизайн, но должны быть разложены в плане по задачам:

- какие из интеграций уже реально поддерживаются на company уровне в `PartyCRM`;
- какие поля `Documents` уже существуют и какие придется вводить впервые;
- что именно из `Notifications` должно считаться company-level;
- нужна ли migration-логика для части настроек, если они ранее жили в другом месте.

## Итог

Рекомендуемая реализация: самостоятельный модуль `Настройки компании` с отдельной веткой app-router, отдельным shell, локальной навигацией и company-level model/API.

Это решение:

- соответствует текущей архитектуре `PartyCRM`;
- повторяет структуру `ArtistCRM` на уровне пользовательского сценария;
- не тащит legacy-подходы из `ArtistCRM`;
- создаёт нормальную базу для постепенной реализации всех страниц.
