# PartyCRM Roles And API Access

## Роли v1

- `owner` — владелец компании. Может управлять компанией, заказами, клиентами, точками, услугами и сотрудниками. Последнего владельца нельзя удалить или понизить.
- `admin` — администратор компании. Может управлять операционными данными компании: заказами, клиентами, точками, услугами и сотрудниками.
- `location_owner` — владелец одной или нескольких площадок. Область задаётся обязательным `PartyStaff.locationIds[]`; роль использует отдельный кабинет и не получает права администратора компании.
- `performer` — исполнитель с аккаунтом. Не получает доступ к company API кабинета компании; видит только свои назначения через `/api/party/performer/*`.
- `contractor` — подрядчик без аккаунта. В БД хранится как `PartyStaff.role = performer` без `authUserId` до ручной привязки аккаунта.
- Глобальная роль `PartyUser.role = dev` получает виртуальный доступ ко всем неархивным компаниям как `owner` без создания `PartyStaff` в БД. Такой доступ помечается `isDeveloperAccess`.

## Матрица доступа v1

| Блок | `owner` | `admin` | `location_owner` | `performer` |
| --- | --- | --- | --- | --- |
| Company workspace `/company/*` | Да | Да | Только `/company/my-locations` | Нет |
| Performer workspace `/performer/*` | Только если есть performer interface role и назначение | Только если есть performer interface role и назначение | Нет | Да |
| Заказы компании | Полный CRUD | Полный CRUD | Чтение и закрытие только заказов своих площадок | Только свои назначения через performer API |
| Клиенты | Полный CRUD | Полный CRUD | Имя и телефон внутри заказа своей площадки | Только минимальный client snapshot в назначении |
| Точки и услуги | Полный CRUD | Полный CRUD | Названия своих площадок и услуг видимых заказов | Только данные точки/адреса назначенного заказа |
| Сотрудники | Полный CRUD, включая передачу владельца | CRUD без назначения нового владельца | Только назначенные на видимый заказ | Нет |
| Финансы заказа | Полная сумма клиента, транзакции, выплаты, маржа | Полная сумма клиента, транзакции, выплаты, маржа | Поступления, расходы и выплаты только видимого заказа | Только своя выплата и статус подтверждения |
| Экспорт финансов CSV | Да, если тариф разрешает статистику | Да, если тариф разрешает статистику | Только по своим площадкам | Нет |

## Правила API

- Company API (`/api/party/orders`, `/api/party/clients`, `/api/party/locations`, `/api/party/services`, `/api/party/staff`) доступны только `owner/admin`.
- `location_owner` по умолчанию отклоняется общим helper доступа и допускается только отдельными `/api/party/location-*` endpoint'ами. Каждый запрос повторно ограничивает заказ по `tenantId` и `locationIds` текущего сотрудника.
- Запись денег владельцем площадки требует `Idempotency-Key`; ключ уникален внутри компании и сотрудника, а операция проходит в MongoDB-транзакции с повторной блокировкой актуальной области площадок.
- Performer API (`/api/party/performer/*`) работает отдельно и возвращает только назначения текущего исполнителя.
- Все company API принимают активную компанию через `x-partycrm-company-id` и проверяют membership пользователя. Для `PartyUser.role = dev` membership строится виртуально по всем неархивным компаниям.
- Все tenant-owned запросы должны фильтровать данные по `tenantId`.
- Публичные auth/profile endpoints (`/api/party/auth/*`, `/api/party/memberships`) не должны возвращать полные операционные данные компании.
- Billing API (`/api/party/billing/*`) работает на выбранную компанию и доступен только `owner/admin`.
- Finance export API (`/api/party/finance/export`) доступен только `owner/admin` и дополнительно проверяет тарифный флаг `allowStatistics`.
- Site settings API (`/api/party/site-settings/*`, `/api/party/tariffs` write endpoints) доступен только глобальной роли PartyUser `dev`.
- Company settings API (`/api/party/company-settings`) доступен только `owner/admin`, а отдельные поля могут быть отфильтрованы тарифными feature flags.
- Management API приглашений `/api/party/staff/[id]/invite` доступен только `owner/admin` выбранной компании.
- Публичная ссылка приглашения назначает только membership-роль `admin` или `performer`; роль `owner` через ссылку не передаётся.
- Роль `location_owner` и список площадок назначаются owner/admin в карточке сотрудника; публичная ссылка не расширяет область прав.

## Прямые URL и route guards

- `/company/*` требует membership в выбранной компании и роль `owner/admin`; для глобальной роли `dev` доступ строится виртуально как `owner`.
- `/company/my-locations` требует активную роль `location_owner` и хотя бы одну действующую площадку; остальные `/company/*` и `/performer/*` для этой роли закрыты.
- `/company/settings` и `/company/settings/[tab]` требуют membership-роль `owner/admin`; глобальная роль `dev` проходит через виртуальный owner-membership выбранной компании.
- `/party/site-settings/*` требует глобальную роль PartyUser `dev`.
- `/performer/*` использует отдельный performer flow и не должен открывать company workspace автоматически.
- При чужом или отсутствующем `x-partycrm-company-id` company API возвращает `403 partycrm_company_access_denied` или `400 partycrm_company_id_required`.

## Видимость данных исполнителя

Исполнитель может видеть:

- свои назначенные заказы;
- дату, время, адрес или точку;
- название/услугу заказа;
- комментарий администратора, предназначенный для подготовки;
- свои выплату и статус подтверждения;
- минимальные данные клиента, необходимые для выполнения заказа.
- свой `confirmationStatus`, `payoutAmount`, `payoutStatus`.

Исполнитель не должен видеть:

- полную сумму клиента;
- предоплату, остаток и историю транзакций;
- валовую маржу и внутреннюю финансовую аналитику;
- внутренние финансовые фильтры;
- список всех клиентов компании;
- список всех заказов компании;
- список всех сотрудников и подрядчиков компании.
- тариф компании, платежи компании и баланс.

## Приглашения сотрудников

- Владелец или администратор создаёт одноразовую ссылку для конкретной карточки `PartyStaff`.
- Ссылка действует 7 дней, может быть перевыпущена или отменена; в БД хранится только SHA-256 хеш токена.
- Телефон аккаунта при принятии должен совпадать с телефоном карточки на момент выпуска.
- Ссылка работает и для нового пользователя после регистрации, и для существующего PartyCRM-аккаунта после входа.
- Сотрудник явно подтверждает подключение кнопкой `Принять приглашение`.
- Повторная membership в той же компании и привязка карточки к другому аккаунту блокируются.

## Правила меню настроек компании

- Все подразделы `Настройки компании` видимы membership-ролям `owner/admin`.
- Глобальная роль `PartyUser.role = dev` видит все неархивные компании через виртуальный owner-membership; `PartyUser.role = admin` без company membership доступа к компании не даёт.
- `Интеграции`, `Уведомления` и `Тарифы` доступны при любом тарифе.
- `Документы` остаются видимыми при любом тарифе, но без `allowDocuments` показывают тарифный gate и переход к тарифам.
- Подразделы настроек компании не помечаются ролевыми звёздами.
- Прямой переход по URL проверяется серверным route guard и не открывается performer.

## Критические проверки

- `getPartyRequestContext`: owner/admin допускаются к `managementOnly`, performer и `location_owner` отклоняются; новая роль разрешается только явным `allowLocationOwner` и не получает управление компанией.
- Прямые URL настроек компании и site settings защищены теми же серверными проверками, что и меню.
- Performer API не возвращает `contractAmount`, `transactions`, `clientPayment`, `balance`, `tariffId`.
- Кабинет площадки не возвращает чужую площадку или заказ, а общие company API отвечают для этой роли 403.
