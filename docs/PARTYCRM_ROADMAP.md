# PartyCRM Roadmap

Рабочее название продукта: `PartyCRM`.

Документ описывает план создания второго продукта на основе опыта и ядра ArtistCRM. Название, домен и финальное позиционирование могут быть изменены до запуска.

---

## Продуктовая гипотеза

PartyCRM — CRM для компаний, которые управляют заявками, площадками, сотрудниками, бронированиями, оплатами и подготовкой мероприятий.

Первичные сегменты:

- праздничные агентства;
- детские игровые и развлекательные точки;
- анимационные команды;
- event-команды;
- фотостудии и студии с несколькими залами/площадками;
- площадки под мероприятия и мастер-классы.

Главное отличие от ArtistCRM:

- ArtistCRM решает задачу соло-артиста: не потерять заявку, контакт, оплату и событие.
- PartyCRM решает задачу компании: контролировать заявки, точки, администраторов, исполнителей, бронирования и операционную подготовку.

---

## Стратегия продукта

- Бренд, домен, лендинг, тарифы и onboarding должны быть отдельными от ArtistCRM.
- На первом этапе не делать полный форк кодовой базы.
- Использовать текущий проект как технологическую платформу и постепенно выделять общий core.
- Данные PartyCRM и ArtistCRM хранить в разных БД/DB namespace с отдельными переменными подключения.
- Не усложнять ArtistCRM функциями для компаний.
- Новые company-функции проектировать так, чтобы они могли жить в отдельном интерфейсе и позже быть вынесены в отдельное приложение/репозиторий.

Целевое состояние:

```txt
ArtistCRM
- solo UI
- личные заявки
- личные мероприятия
- простые оплаты и документы

PartyCRM
- company UI
- точки/залы/площадки
- сотрудники и роли
- назначения исполнителей
- бронирования и конфликты
- выплаты исполнителям
- чеклисты администраторов

Общее ядро
- auth/tenants
- clients
- events/orders
- payments/transactions
- documents
- reminders
- public leads API
```

## Архитектура данных

Принятое решение: не смешивать данные ArtistCRM и PartyCRM в одной базе данных.

На старте:

```txt
ArtistCRM
- домен: artistcrm.ru
- БД: ArtistCRM production database
- env: MONGODB_URI / MONGODB_DBNAME

PartyCRM
- домен: partycrm.ru
- БД: PartyCRM production database
- env: MONGODB_URI / MONGODB_DBNAME
```

Правила:

- В коде должен быть явный product/database context: `artistcrm` или `partycrm`.
- Нельзя выбирать БД неявно только по пользовательским данным.
- Все API PartyCRM должны работать только с PartyCRM DB.
- Все API ArtistCRM должны продолжать работать только с ArtistCRM DB.
- Общие модели можно переиспользовать, но подключение к Mongoose/MongoDB должно быть product-aware.
- Даже при отдельной БД сохраняем `tenantId` во всех tenant-owned сущностях PartyCRM, потому что внутри PartyCRM будет несколько компаний.
- Миграции, seed-данные, backup и restore должны выполняться отдельно для каждой БД.

Причина решения:

- меньше риск случайного смешивания клиентских данных;
- проще юридически и операционно объяснять изоляцию продуктов;
- проще будет выделить PartyCRM в отдельный проект/репозиторий, если продукт подтвердится;
- меньше риск, что company-схемы и нагрузки начнут влиять на solo-продукт.

### Multi-company and contractor model

Принятое целевое решение: один аккаунт входа не равен одной компании.

Базовые сущности:

```txt
User
- глобальный аккаунт авторизации;
- может быть связан с несколькими компаниями;
- может одновременно быть владельцем, администратором и исполнителем в разных компаниях.

PartyCompany
- отдельная компания/организация внутри PartyCRM;
- имеет собственные точки, сотрудников, заказы, выплаты и настройки.

PartyStaff
- карточка участия человека в конкретной PartyCompany;
- всегда принадлежит одному tenantId;
- может быть привязана к User через authUserId;
- может быть не привязана к User, если это подрядчик без аккаунта.
```

Правила:

- Один `authUserId` может иметь несколько `PartyStaff` записей в разных `tenantId`.
- Один пользователь может управлять несколькими компаниями через переключатель компании.
- Кабинет компании работает в контексте активной компании.
- Кабинет исполнителя должен уметь показывать назначения из нескольких компаний.
- Подрядчик без аккаунта может быть добавлен в компанию и назначен на заказ.
- Автоматической привязки подрядчика к аккаунту по телефону не делаем.
- Если появился зарегистрированный пользователь с совпадающим телефоном, компания видит индикатор и может инициировать ручную привязку.
- Исполнитель должен подтвердить привязку аккаунта к карточке подрядчика.
- История заказов и выплат должна оставаться в компании даже при архивировании сотрудника.

Причина решения:

- реальный исполнитель может работать с несколькими агентствами;
- владелец может вести несколько компаний или филиальных юрлиц;
- компаниям нужно учитывать подрядчиков до их регистрации в системе;
- ручная привязка безопаснее автоматической, потому что телефон может быть ошибочным, переиспользованным или общим.

Проверки выполняются на изолированных тестовых данных и mock API, без обращения к рабочей БД или отправки внешних уведомлений. Состояние более широких исторических эпиков PC-RP4/PC-AO1/PC-ORG6 сохраняется независимо от этих критериев.

Основание: ответы пользователя на вопросы по неудобству работы с заказом, должностями, задачами, контактами, отчётами и брифом, включая восемь заключительных уточнений от 2026-10-27. Это согласованные требования; реализация и результаты приёмки перечислены выше. При расхождении с историческими описаниями MVP для новой переработки применяются решения этого раздела; руководства текущего интерфейса обновляются при реализации. Основной продуктовый принцип — настраиваемая модель для разных компаний без закрепления полномочий за названием конкретной должности. Описание рабочего процесса пилотной компании ожидается отдельно и не является условием начала работ. Дополнительных обязательных вопросов для завершения планирования нет; перечисленные ниже проектные предложения реализуются в пределах согласованных требований.

**Принятые требования**

- Должности (PC-RP4/PC-AO1): у сотрудника ровно одна должность в конкретной компании; одну должность могут занимать несколько сотрудников. Текущие роли, включая администратора, сохраняются; руководитель может создавать новые. Совмещение должностей, персональные исключения и временное замещение пока не включать.
- Права должности задаются для разделов, отдельных полей и действий: скрыто, просмотр, изменение; создание, удаление, назначения, финансовые операции и проверка отчётов требуют собственных разрешений. Клиентские суммы, платежи, гонорары, фактические выплаты, расходы и маржа разделяются. Менеджер может не видеть состав исполнителей; худрук может видеть клиента и дату без права их менять, назначать исполнителей и вносить их оплату при соответствующих правах.
- Допускается ограничение должности одной или несколькими площадками. Видимость заказа зависит от его этапа: новая внешняя заявка может быть доступна только уполномоченным менеджерам до передачи дальше. Настраиваемые этапы заказа проектируются отдельно от системных `draft/active/canceled/closed` и от этапов переписки. Правило не должно проверять текстовое название должности «Менеджер».
- Права проверяются на сервере и в интерфейсе, включая выдачу полей, изменение отдельных данных, прямые URL, экспорты, вложения, push и календарь. Назначение задачи не открывает весь заказ автоматически. При недостатке полномочий нужен безопасный контекст и понятное объяснение, почему действие выполнить нельзя, без раскрытия закрытых данных.
- Контакты (UX-переработка PC-ORG6): вместо двух блоков «Роли контактов и правила связи» и «Доп. контакты» — основной клиент и дополнительные контакты по образцу «Ведело», с произвольным полем «Кем является». В заказе отдельно отмечается доступность основного и дополнительных контактов исполнителям; должность остаётся верхней границей доступа. Памятка способов связи задаётся каждому контакту и ничего технически не блокирует.
- При упрощении контактов сохранить прежние данные и внутренние связи партнёра/плательщика/контакта на месте. Плательщик уже используется как предложенный клиент в общем поступлении; произвольная подпись контакта не должна автоматически менять финансовый смысл. Сохранить tenant-проверки, объединение/защиту удаления клиентов и совместимость старого API. Специальную инструкцию «От чьего имени представляться» предлагается объединить с необязательной инструкцией команде без потери заполненного текста.
- Подсказки: для неочевидных полей добавить значок `i` по образцу `FieldHelp` проекта «Ведело», открываемый нажатием и доступный с клавиатуры/телефона. Первые кандидаты — связи вопросов отчёта с услугой, площадкой и реквизитом, условия показа и проверяющая должность. Подсказка объясняет назначение и даёт короткий пример.
- Телефоны: пока `+7`, с возможностью расширения в будущем; одинаковая нормализация обычной вставки и кнопки для `+7`, `7`, `8` и десятизначного номера. Правая кнопка вставки заменяет номер целиком; при нескольких номерах в буфере показывается выбор. Копирование/вставка — по образцу «Ведело»; на авторизации/регистрации новые кнопки не добавлять. Пример: `89138370020` → `+7 (913) 837-00-20`.
- Задачи (PC-ORG13 и развитие PC-OF6): связаны с заказом или самостоятельны. В первой версии создавать может любой сотрудник; изменение срока/содержания, переназначение и отмена — администратор или должность с соответствующим правом. Назначение возможно конкретным сотрудникам и должности; задача должности доступна всем её сотрудникам в разрешённой области. Достаточно выполнения одним с фиксацией автора и времени; главного ответственного нет.
- Задачи получают ровно четыре статуса: «Новая / В работе / Выполнена / Отменена», форматируемое описание с медиа и быстрый выбор сроков по образцу «Ведело». Приёмка руководителем и дополнительные статусы в первый выпуск не входят. При изменении даты заказа сроки не сдвигаются автоматически; срок задачи после даты исполнения вызывает предупреждение. Отмена заказа отменяет оставшиеся незавершённые задачи и уведомляет участников, история выполнения сохраняется.
- Повторяющиеся задачи входят в первый выпуск. Реализация: настраиваемое правило, начало/окончание повторений и время в часовом поясе компании; каждый срок создаёт отдельный экземпляр со своим статусом и историей. Завершение/отмена одного экземпляра не отменяет всю серию. Отдельная отмена серии прекращает будущие экземпляры, не уничтожая историю; отмена заказа также останавливает серии, привязанные к нему. Повторный запуск планировщика не дублирует один экземпляр.
- Напоминания по задачам адресуются пользователю или сотрудникам назначенной должности с учётом их настроек каналов. Все уполномоченные участники назначения видят общую задачу в CRM и в своих подключённых личных календарях; взятие в работу не делает задачу исключительной собственностью одного сотрудника. Обновления и выполнение синхронизируются у всех; календарные записи представляют одну общую задачу. Общий календарь компании в первый выпуск не добавлять. Увольнение/неактивность ответственного не должны молча терять задачи — администратор получает список для решения.
- Отчёты (UX-переработка PC-ORG14/PC-ORG7): основной сценарий — личный отчёт каждого исполнителя; координатор необязателен. Вопросы настраивает компания, пример краткой формы: «Как прошло мероприятие?» и «Были ли сложности?». Проверка назначается должности, достаточно решения одного уполномоченного сотрудника с фиксацией автора. Начатый отчёт сохраняет исходную версию формы.
- Единая кнопка «Отчёт» открывает форму конструктора компании. По подтверждению пользователя прежних отчётов нет: поддержку, миграцию и отдельный просмотр старого текстового формата не реализовывать, прежний рабочий путь исключить. Это решение относится к прежнему формату отчёта PartyCRM; оно не отменяет сохранность текущих снимков настраиваемых форм, финансового учёта, данных брифов и сценариев ArtistCRM.
- Сообщение «Нет форм отчёта» требует раздельного объяснения причин и предпросмотра от лица исполнителя. По коду возможны несохранённая/неактивная форма, отсутствие подходящих полей по условиям или только командная форма без прав координатора; причина в рабочей компании пока не установлена. В настройках формы задаются срок сдачи и два независимых условия: блокировать закрытие заказа без принятого отчёта; блокировать выплату конкретному исполнителю без принятого личного отчёта. Проверки действуют и на сервере; отсутствие отчёта одного участника само по себе не блокирует выплату другим.
- Бриф (UX-переработка PC-ORG2): один настраиваемый шаблон компании, комментарии менеджера по разговору и чеклист важных вопросов. Название «Бриф» сохраняется. Заполняет менеджер, видимость определяется должностью. Все настроенные поля обязательны независимо от статуса, но неполную входящую заявку/черновик можно сохранить: недостающее показывается явно и требуется перед передачей на следующий рабочий этап. Приём внешнего API до разговора с клиентом не блокируется. Поля, участвующие в действующей бизнес-логике, и ранее заполненные ответы сохранить.
- Новая версия брифа применяется к незакрытым заказам; закрытые сохраняют исходную версию. Исключение вопроса из шаблона не удаляет его заполненные ответы или вложения. Перед применением редактор шаблона видит изменения и последствия для незакрытых заказов; для исключённого вопроса предлагает «Убрать вопрос, сохранить ответы в истории» либо «Оставить вопрос». Уничтожение ответов в этом сценарии не допускается. Переименование вопроса не меняет его постоянный идентификатор.
- Автоматические оповещения об изменении брифа и подтверждения ознакомления не добавлять. Если изменение важно команде, менеджер самостоятельно пишет комментарий исполнителям.
- Основной кандидат интерфейса — компактная форма заказа, показ разрешённых блоков и полей, срочные задачи и быстрые звонки/переходы в чат с телефона. Предложенный способ реализации — единый рабочий сценарий с меню по доступным функциям, без обязательной полной переписки существующих внутренних маршрутов. В целевой модели исходная роль исполнителя видит имена, контакты и функции коллег без их выплат; конкретный доступ определяется настройками должности.

**Очередность реализации**

1. Зафиксировать границы должности, этапов и задач; инвентаризировать поля/действия и текущие API, чтобы предварительные UX-изменения вписывались в будущие права.
2. Исправить телефонные поля и добавить подсказки `i`; упростить контакты с сохранением прежних связей; сделать единый вход в отчёт компании и объяснять причины отсутствия подходящей формы. Поддержка прежнего текстового отчёта не требуется.
3. Развить PC-ORG13: единая модель задач с необязательной связью с заказом, людьми/должностью, четырьмя статусами, медиа, историей и повторениями уже в первом выпуске. Перенести доп. события без дублирования задач; личные календари отражают общую задачу для всех уполномоченных участников. Пункты подготовки показывать как связанные задачи без копий, сохранив специальные проверки готовности заказа.
4. Развить PC-RP4/PC-AO1: настраиваемые должности, действия и поля, области площадок, этапы заказа/переходы, серверная фильтрация и безопасное изменение разрешённых полей, предпросмотр доступа. Должность не подменяет глобальную роль аккаунта или функцию сотрудника в заказе.
5. Упростить конструктор отчёта и добавить конструктор брифа, проверяющих по должности, сроки сдачи и независимые блокировки закрытия/выплаты. Начатый отчёт сохраняет снимок формы; новый бриф обновляет незакрытые заказы с сохранением ответов исключённых вопросов, закрытые заказы сохраняют исходную версию. Финансовый учёт и скрытые поля при сохранении не теряются; автоматических уведомлений об изменении брифа нет.
6. Проверить реальные сценарии разных должностей, площадок и этапов, мобильный ввод/срочные задачи/контакты, прямые API/URL, уведомления, вложения и личные календари. Новую модель готовить для всех ролей, а не ограничивать одним названием должности. До включения показать сопоставление нынешних доступов и новых настроек.

**Проектные решения для реализации**

- Заказы: предоставить настраиваемые компанией этапы/переходы, начальный этап API-заявок и права передачи дальше. Для площадок явно предусмотреть выездные заказы и заявки с ещё не выбранным местом. Конкретный маршрут и обязательные условия задаёт компания, а не название должности в коде.
- Кабинет: использовать компактную форму и меню по доступным функциям, сохраняя существующие внутренние маршруты там, где это уменьшает объём изменений. Единый внешний рабочий сценарий и живая очередь должности — предложенные способы реализации; персональные исключения и совмещение должностей не добавляются.
- Задачи: в очереди должности учитывать текущий состав активных сотрудников. Пункты чеклиста подготовки связать с общей очередью без копирования, специальные состояния сборки/сверки клиента не превращать механически в обычные задачи. Для повторений использовать правило и период действия серии, часовой пояс компании, независимый статус каждого экземпляра и защиту от дублей планировщика.
- Отчёты: компания настраивает срок и обе независимые блокировки; фиксированное время сдачи для всех компаний не задавать. Право проверить отчёт и право провести выплату разделяются. Удаление прежнего пути отчёта не должно отключить финансовую сверку и проверки действующей формы.
- Бриф: постоянные идентификаторы вопросов, версии шаблона и история ответов исключённых вопросов. Переименование сохраняет идентификатор; новый смысл или несовместимый тип ответа получает новый идентификатор, прежний ответ сохраняется в истории. Обновление изменяет только бриф, сохраняет актуальные ответы и повторно проверяет ревизию/статус заказа; закрытый параллельно заказ не обновляется по устаревшему состоянию. При одновременной правке менеджером перечитать данные и совместить с новой структурой, не перезаписывать ответы старым снимком.
- Дополнительные типы ответов сверх rich-text/фото и клиентская ссылка на бриф пока не включаются. Существующая творческая библиотека не расширяется в рамках этой переработки. Автоматизация ознакомления с брифом исключена по прямому ответу пользователя.

**Критерии приёмки**

1. Пользовательская должность разрешает просмотр клиента/даты без изменения, может полностью скрыть команду или реквизит и ограничить конкретное действие. Скрытые поля не возвращаются через альтернативный API/экспорт/уведомление; сохранение разрешённых полей не стирает остальное. Прямой переход по URL повторяет ограничения.
2. Начальная API-заявка видна только разрешённым должностям; смена этапа меняет доступ по настройкам. Заявки без площадки не пропадают из разрешённой очереди. Входящая заявка и черновик сохраняются без полного брифа, но дальнейшая передача проверяет обязательные вопросы.
3. Обычная вставка и правая кнопка одинаково обрабатывают номера с `8`, `7`, `+7` и без префикса. Кнопка заменяет номер целиком; несколько найденных номеров предлагают выбор. Кнопки копирования/вставки отсутствуют на авторизации/регистрации.
4. Дополнительный контакт имеет свободную роль, отдельную памятку связи и разрешение показа исполнителю. Исполнитель получает только доступные ему контакты с учётом должности; прежние данные заказа и финансовые связи плательщика сохраняются.
5. Одна коллективная задача видна всем уполномоченным участникам в CRM и подключённых личных календарях. Первый успешный переход в «Выполнена» фиксирует одного автора и время; одновременное/повторное нажатие не создаёт второе выполнение. Используются только четыре согласованных статуса, без приёмки.
6. Повтор задачи создаёт самостоятельный экземпляр ровно один раз при повторе/гонке планировщика. Завершение/отмена одного экземпляра не отменяет будущие; отмена серии прекращает будущие без потери истории. Отмена заказа отменяет его открытые задачи и дальнейшие связанные повторы с уведомлением участников.
7. Перенос заказа не меняет сроки задач; несоответствие сроков показывает предупреждение. Задачи неактивного сотрудника видны администратору для решения. Уведомления и личные календарные записи учитывают текущие полномочия и настройки пользователя.
8. Одна кнопка «Отчёт» открывает актуальную форму компании. Если подходящей формы нет, объясняется причина. Прежняя текстовая форма не предлагается; миграция старых отчётов не выполняется. Неочевидные настройки имеют доступную с телефона подсказку `i`.
9. Срок сдачи и блокировки закрытия/выплаты настраиваются отдельно и проверяются сервером. Проверяет сотрудник назначенной должности, достаточно одного решения с авторством. Отчёт другого исполнителя не блокирует выплату сотруднику, выполнившему требования. Начатый отчёт сохраняет исходные вопросы при изменении шаблона.
10. Новая версия брифа обновляет незакрытые заказы; закрытые сохраняют исходный снимок. Переименование сохраняет ответ, новый вопрос появляется пустым, исключённый вопрос сохраняет прежнее название, ответ и вложения в истории с прежними ограничениями доступа.
11. Перед публикацией брифа показаны добавляемые, изменяемые и исключаемые вопросы и затрагиваемые заказы. Редактор может оставить вопрос либо убрать его с сохранением ответов в истории. Параллельное закрытие/редактирование заказа и безопасный повтор применения не приводят к потере данных или дублям.
12. Изменение брифа не создаёт автоматических оповещений и подтверждений прочтения. Менеджер может самостоятельно оставить комментарий исполнителям. Компактная форма, срочные задачи и переходы к звонку/чату проверены на телефоне.

## Что не входит в MVP

- Полноценный склад и учет реквизита.
- Сложный график смен.
- Зарплатные ведомости с налогами и бухгалтерией.
- Франшизы и многоуровневые филиалы.
- Брендирование под клиента.
- Совмещение нескольких должностей у сотрудника, персональные исключения из прав и временное замещение (отложены по уточнению 2026-10-26). Настройка прав должности до полей и действий включена в текущую переработку PC-RP4/PC-AO1.
- Сложная BI-аналитика.
