# Заказы, аренда и приглашения — 1.33.0

## Настройка компании

Настройки доступны участникам компании с ролью `owner` или `admin`. Глобальная
роль аккаунта не заменяет участие в компании. Ограничения должностей продолжают
действовать для чтения заказов, клиентов и финансов.

1. В «Типах заказов» создайте типы со стабильными идентификаторами. Для каждого
   типа настройте бриф; архивирование скрывает тип из нового оформления.
2. В «Аренде и графике» задайте недельный график компании и исключения по датам.
   Это отдельный график, он не связан с часами ответа менеджеров.
3. В карточке помещения укажите почасовую ставку, подготовку/уборку и, при
   необходимости, собственный график. Одно независимо бронируемое помещение —
   одна запись справочника площадок.
4. В услуге настройте цену и длительность одного выполнения, доступные типы и
   помещения, возможность выезда, повторность и включённые минуты аренды.
   При настроенных ограничениях услуга должна подходить одновременно типу и месту.
   Старые услуги без явной настройки ограничений сохраняют прежнюю доступность.
5. В «Приглашениях» подготовьте шаблоны из готовых блоков. Для типа можно выбрать
   шаблон по умолчанию. Используются существующие изображения компании.

Бриф поддерживает короткий/развёрнутый текст, число, дату, время, дату со временем,
денежную сумму, выбор, флаг, контакт и информационную заметку. Заметка не требует
ответа. Сохраняются порядок, обязательность, условные вопросы по услугам и
предпросмотр. Контакт можно выбрать из клиентов либо создать отдельно; он не
заменяет основного клиента заказа и не объединяется автоматически с похожими.

## Оформление

В рабочем разделе «Заказы» создание открывается в отдельной модальной форме.
На телефоне форма занимает экран, основные действия закреплены внизу.

С версии 1.34.0 сначала открывается короткая «Новая заявка»: клиент и внутренняя
заметка по разрешённым полям. Её можно сохранить без неизвестных деталей,
включая компанию без настроенных типов. «Оформить бронирование» продолжает
заполнение полного мастера; сохранённая заявка оформляется дальше в той же записи.
Восстановление прерванного мастера в текущей вкладке и навигация описаны в
[руководстве UX](PARTYCRM_ORDER_UX.md#быстрая-заявка-и-навигация--1340).

Последовательность: тип → помещение/выезд → услуги → время → клиент и бриф →
финансы. Отдельное название не вводится: заголовком становится снимок названия
типа. Дата и клиент помогают различать заказы одного типа.

Неполную заявку можно сохранить черновиком на любом шаге. Завершение требует
типа, клиента, корректного времени и обязательных ответов. При отсутствии графика
свободное время не предлагается; черновик остаётся доступен.

Несовместимые услуги после смены типа/места показываются явно. Менеджер удаляет
их сам. Условия сохранённых позиций не меняются при редактировании справочника;
неизменённые старые позиции не мешают несвязанным изменениям заказа. Количество
новых повторов целое, у неповторяемой услуги — один. Исторические дробные позиции
сохраняются. Дополнительные согласованные позиции КП учитываются в расчёте.

Редактор заказа также открывается отдельно. В нём остаются команда, задачи,
отчёты, документы и расширенные действия. Просмотр — самостоятельный режим:
редактирование включается только явной кнопкой и при наличии права.

В задаче, списке и на доске доступны «Посмотреть заказ» и «Карточка клиента»
в пределах разрешений. Окна загружают запись по ID, а закрытие сохраняет
открытую задачу, фильтры и позицию списка. Доступ к задаче не даёт доступа к
скрытому заказу, клиенту или финансам.

Рабочий список сортируется на сервере по созданию, дате мероприятия или доступной
договорной сумме. По умолчанию новые записи идут первыми. Заказы без даты идут
после датированных при обоих направлениях сортировки по мероприятию. Выбор
сохраняется в браузере отдельно для сотрудника и компании. Календарь сохраняет
временной порядок. Составной курсор связан с сортировкой и фильтрами; при их
изменении загрузка начинается с первой страницы.

## Программа и аренда

Длительность программы равна сумме длительностей всех выполнений услуг.
Параллельных услуг пока нет. Аренда имеет собственные начало и окончание и должна
полностью вмещать программу. В заказе только аренды программа совпадает с арендой.

```text
Программа, мин = сумма(длительность × количество)
Включённая аренда, мин = сумма(включённые минуты × количество)
Платные минуты = max(0, длительность аренды − включённая аренда)
Аренда, ₽ = ceil(платные минуты / 60) × почасовая ставка
Итог, ₽ = услуги + аренда − скидка
```

Например, из 150 минут аренды 60 включены в услуги. Остаётся 90 минут, оплачиваются
два часа. Фактическая бронь при этом длится 150 минут. Подготовка и уборка занимают
помещение, но не прибавляются к клиентской аренде. Для выезда аренда помещения не
применяется. Скидка задаётся одним способом — суммой либо процентом, до полной
стоимости. Расчёты выполняются в целых копейках; совместимые денежные API-поля
остаются в рублях.

Календарь предлагает начало с шагом 15 минут, сохраняя точную длительность.
Учитываются график, исключения, аренда других заказов, билетные сеансы, буферы,
эксклюзивность/совместность и вместимость. Выезд использует график компании.
Проверки команды и реквизита продолжают действовать отдельно.

Доступность предварительная. Запись повторно проверяет бронь под блокировкой
помещения в MongoDB-транзакции. При конфликте форма сохраняет введённые данные.
Для новых бронирований и атомарных финансовых операций нужен replica set.
Ранее сохранённые заказы без арендных полей используют прежний интервал.

## Приглашение

В заказе доступны создание, предпросмотр, публикация, копирование ссылки и
отключение. Страница общая для всех гостей, публичный токен непредсказуемый.

В публикацию попадают только блоки приглашения и явно выбранные публичные
контакты. Бриф, финансы и карточка клиента не публикуются. Текст и оформление
сохраняются снимком; новые изменения шаблона их не перезаписывают. Дата, время
и место берутся из сохранённого заказа. После отключения, отмены или удаления
заказа ссылка не работает; повторная публикация создаёт новый токен.
Публичная страница исключена из офлайн-кэша и индексации.

Ответы гостей, персональные ссылки, рассылка и экспорт в изображение/PDF в выпуск
не входят.

## API и переход данных

- Типы: `GET/POST/PATCH /api/party/order-types`.
- Брифы: существующие endpoints брифов с `orderTypeId`; версии разных типов
  независимы. Закрытый заказ хранит снимок. Исключённые ответы и ответы прежнего
  типа сохраняются в истории.
- График компании: `GET/PUT /api/party/booking-settings`; ставка и график помещения
  в существующем API площадок.
- Доступность: `POST /api/party/orders/availability`; только свободные интервалы,
  без названий чужих заказов.
- Оформление: существующие create/update с `bookingVersion: 1`, `orderTypeId`,
  `serviceSelections`, `rental`, `discount`, `completeBooking`. Сервер формирует
  снимки, `servicesIds`, `title`, окончание программы и стоимость.
- Сортировка рабочего списка: `view=list&sortBy=created_desc|created_asc|event_asc|event_desc|amount_asc|amount_desc`,
  продолжение через `listCursor`. Старый формат запроса без `sortBy` сохранён.
- Ожидания: см. [руководство по финансам](PARTYCRM_ORDERS_FINANCE.md).
- Шаблоны: `/api/party/invitation-templates`; приглашение заказа:
  `/api/party/orders/:id/invitation`; публичное чтение: `/invitation/:token`.

Все защищённые операции проверяют компанию, membership, область записей и маски
полей. Сначала мигрируется только настроенный строковый справочник типов.
Для однозначного связывания исторических заказов предусмотрена повторяемая CLI:

```powershell
npm run party:migrate-order-types
npm run party:migrate-order-types -- --company=OBJECT_ID
npm run party:migrate-order-types -- --apply
```

По умолчанию это просмотр количеств без записи. `--apply` создаёт недостающие типы
и заполняет ссылки при точном нормализованном совпадении. Произвольные названия
не создают типы. Цены, длительности, `title` и документы не пересчитываются.
CLI использует окружение Next.js; перед применением выбирайте нужную базу и
штатную резервную копию. В рамках разработки миграция рабочей базы не запускается.

## Проверка

```powershell
npm test
npm run test:party-booking:mongo
npm run test:party-finance:mongo
npm run test:party-booking:browser
npm run build
```

Mongo-проверки запускают собственный временный replica set, не загружают URI
рабочей базы и завершают только свой процесс. `MONGOD_BINARY` задаёт бинарник
mongod. Браузерная проверка требует готовую production-сборку и установленный
Playwright (`PLAYWRIGHT_MODULE` при необходимости), путь браузера можно передать
в `PLAYWRIGHT_EXECUTABLE_PATH`. Бинарные снимки интерфейса не сохраняются.
