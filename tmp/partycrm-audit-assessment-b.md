## Подтверждённые проблемы

### B1 — [P1] Контраст активной навигации и основной кнопки ниже WCAG AA

**Категория:** Accessibility. **Стандарт:** WCAG 1.4.3 Contrast (Minimum), текст 14px/600 требует 4.5:1.

**Источник:** `PartyAppShell.js:257–260` и `:273–276`: активные `MenuLink` / `MenuGroupButton` используют `bg-sky-500 text-white`. `PartyRoleOrdersWorkspace.js:1854` и `:1892–1895`: `+ Заказ` и выбранное представление используют `bg-sky-600 text-white`.

**Фактические live computed styles на `/company/work`, 1280×720:**

```text
aside a «Заказы»:
  background = oklch(0.685 0.169 237.323)
  color = rgb(255, 255, 255)
  fontSize = 14px; fontWeight = 600
button «+ Заказ»:
  background = oklch(0.588 0.158 241.966)
  color = rgb(255, 255, 255)
  fontSize = 14px; fontWeight = 600
```

Палитра подтверждена текущим `node_modules/tailwindcss/theme.css:123–124`; `tailwind.config.js:33–55` не переопределяет sky. Расчёт OKLCH → linear sRGB, ограничение каналов в gamut [0,1], затем относительная яркость WCAG:

- white / sky-500: **2.713:1**;
- white / sky-600: **4.016:1**.

Это расчёт по реальным computed CSS, не pixel sampling и не оценка по внешнему виду. Оба значения ниже 4.5:1; sky-500 также ниже 3:1 для крупного текста. У человека с пониженным зрением хуже читаются текущий раздел и действие создания.

**Рекомендация:** выбрать фон/цвет текста с измеренным AA-контрастом для обычного текста и распространить исправление на одинаковые состояния. Размер кнопок здесь не проблема. Команда: `$impeccable colorize`, затем `$impeccable audit`.

### B2 — [P1] Раскрытие боковых разделов не имеет программного состояния

**Категория:** Accessibility. **Стандарт:** WCAG 4.1.2 Name, Role, Value — состояние disclosure-контрола должно определяться программно.

**Источник:** `PartyAppShell.js:268–287`, `MenuGroupButton`. React prop `open` только поворачивает декоративную стрелку (`rotate-180`); на `<button>` нет `aria-expanded` и `aria-controls`. Этот общий компонент используется для настроек компании, кабинета и сайта в desktop и mobile меню.

**Live проверка:** кнопка «Настройки компании» успешно раскрывает раздел по Enter, в AX появляется 15 вложенных ссылок. До/после раскрытия DOM чтение возвращает `aria-expanded = null`, `aria-controls = null`. В AX у кнопки нет collapsed/expanded. Это не отсутствие клавиатурной работоспособности; клавиатура работает, отсутствует доступное состояние.

**Влияние:** пользователь скринридера слышит обычную кнопку и не знает, раскрыт раздел или закрыт, пока не исследует следующий контент.

**Рекомендация:** `aria-expanded={open}`, стабильный id контейнера и `aria-controls`; сохранить существующий Enter/Space. Вдобавок `MenuLink` и `SubMenuLink` (`:252–303`) не имеют `aria-current`, хотя active известен. Для «Заказы» это подтверждено live: `aria-current = null`. `aria-current="page"` уже корректно реализован в нижнем `PartyMobileNav.js:40` и может служить образцом. Отсутствие `aria-controls` само по себе не объявляется отдельным нарушением. Команда: `$impeccable harden`.

### B3 — [P2] Ошибка шага объявляется, но не связана с полем и не переводит к нему

**Категория:** Accessibility / восстановление после ошибки.

**Источник:** `PartyOrderWizard.js:252–268`, `:395–398`, `:433–439`, `:498–523`. Валидация даёт конкретный текст в footer `role="alert"`, но на соответствующих полях не выставляются `aria-invalid`, `aria-describedby`; нет фокуса на ошибочном поле. Тип/место/дата/клиент проверяются вручную; обязательность не обозначена `required`/`aria-required` или видимым маркером. Само отсутствие атрибута required при custom validation не объявляется отдельным нарушением WCAG.

**Live воспроизведение:** пустой новый заказ → «Далее» → «Выберите тип заказа.». Фокус остаётся на «Далее». SELECT типа имеет accessible name «Тип заказа», но `required=false`, `aria-required=null`, `aria-invalid=null`, `aria-describedby=null`. Ошибка присутствует в `role="alert"`; говорить, что её совсем не объявляют, неверно.

**Влияние:** пользователь получает понятную общую ошибку, однако повторное исследование поля не сообщает его ошибочность и не связывает с объяснением. При длинном шаге брифа это особенно увеличивает обратную навигацию.

**Рекомендация:** привязать сообщение к проблемному контролу, пометить ошибочное состояние, при провале перехода переводить фокус на первый проблемный контрол либо на фокусируемую сводку с переходом к нему; добавить понятную обязательность. Команда: `$impeccable harden`.

### B4 — [P2] Возврат на прежний шаг закрывает прямой путь к уже пройденным следующим

**Категория:** Implementation Integrity / эффективность мастера.

**Источник:** `PartyOrderWizard.js:84`, `:410–411`, `:434–438`, `:480–487`. Единственное состояние `step` одновременно задаёт текущий экран и доступность progress-кнопок: `disabled={disabled || index > step}`. Максимальный достигнутый шаг не хранится.

**Подтверждено статически, поздние шаги live не пройдены:** если человек уже на «Финансы» и возвращается на «Место» (`setStep(1)`), шаги «Услуги»…«Финансы» снова disabled. Для возврата на финансы требуется 4 последовательных нажатия «Далее» при сохранённых корректных данных. Изменение более раннего поля может действительно потребовать перепроверки зависимостей, но повторный проход навязан даже без изменения данных.

**Рекомендация:** отдельно хранить доступные/пройденные шаги; разрешать переход к валидным пройденным, перепроверяя зависящие данные. Это не предложение убрать текущую проверку бронирования. Команда: `$impeccable distill` либо `$impeccable harden`.

## Дополнительные подтверждения и ограничения

### Мобильное меню: риск виден в коде, мобильное воспроизведение не выполнено

`PartyAppShell.js:821–825`: верхний hamburger имеет постоянное имя «Открыть меню», но не имеет `aria-expanded`/`aria-controls`, даже когда меню открыто. Нижнее «Ещё» в `PartyMobileNav.js:48–52`, напротив, имеет `aria-expanded`.

Контейнер выезжающего меню (`PartyAppShell.js:839–1009`) — fixed overlay между шапкой и нижней навигацией, без механизма Escape, перевода/возврата фокуса и без inert для перекрытого содержимого. Это проверенное отсутствие в данной реализации, но **не live утверждение** о конкретном фокус-трапе на мобильном устройстве. Проверка клавиатурного обхода в mobile viewport нужна, прежде чем давать отдельную оценку severity. В B не сделано: viewport capability браузерная и могла помешать параллельным A/root; мобильную часть ведут они. Не было синтезированного touch и физического телефона.

### Данные демокомпании не позволяют пройти весь новый заказ

На первом шаге доступен только «Выберите тип»; отображается «В компании пока нет типов. Владелец или администратор может добавить их в настройках». Есть ссылка «Настроить типы заказов». По коду отсутствие типа блокирует «Далее», но «Сохранить заявку» вызывает `save(false)`, обходящий полную пошаговую проверку. B не нажимала сохранение и не добавляла типы.

Следовательно, live B не проверяла шаги «Место»…«Финансы», создание нового клиента, аванс, успешное завершение заказа или серверную ошибку. Это ограничение тестового набора, а не доказанный сбой всего приложения. Возможность оформить черновик предусмотрена кодом.

### Производительность: измеренных задержек нет

Нет сетевых таймингов, CPU trace, bundle analysis, LCP/INP или профиля React. Время ответа CUA/первой компиляции не используется как пользовательская задержка. Размер исходного файла не трактуется как размер бандла. Отдельного perf-дефекта B не объявляет.

Подтверждено в исходниках:

- Новый `/company/work` параллельно получает order-options и workflow (`PartyRoleOrdersWorkspace.js:1455–1458`); при открытии нового заказа уже полученные options передаются мастеру (`:1625`, `:2249`).
- Список, доска, календарь и wizard загружаются через dynamic imports (`:66–86`); данные списка/доски запрашиваются только для эффективного представления (`:1554–1598`).
- Поиск списка/доски имеет debounce 250ms и AbortController; availability — debounce 250ms и abort cleanup (`PartyOrderAvailabilityPicker.js:43–89`).
- Старый `CompanyWorkspaceClient.js:502–610` сначала ждёт memberships, затем 9 параллельных запросов вне зависимости от section; это подтверждённая зависимость загрузки, но без измерений не называется «медленной» и не переносится на новый `/company/work`.
- Параллельный пакет старого кабинета завершается общей ошибкой при падении любого запроса, кроме специально обработанного calls/403. Это факт coupling, без воспроизведения сбоя не отдельный инцидент.

### Темизация

В scope последовательно используются Tailwind sky/slate и white; семантические токены PartyCRM для поверхностей/текста здесь не используются (`PartyOrderWizard.js:23–26`, `PartyAppShell.js:672`). Само это не доказывает визуальной несогласованности. PRODUCT.md требует сохранения текущего оформления.

Глобальная `body.theme-dark .bg-white` меняет фон (`app/globals.css:131`), а локальные slate/sky цвета не имеют dark-вариантов. Однако применимость тёмной темы к PartyCRM и реальный способ попасть в неё в этом кабинете не проверены. Поэтому утверждение «в PartyCRM сломан dark mode» и отдельный балл за dark mode **не даются**. Визуальный тест темы после законного включения нужен отдельно; DOM/CSS не мутировались.

### Адаптивность и размеры целей

Код мастера использует min-w-0, min-h-11, перенос progress-кнопок, sm-сетки и полноэкранный Modal на <768px. Footer модалки не прокручивается вместе с body и учитывает safe-area (`components/Modal.js:122–187`). Нижняя навигация имеет min-h-16 и safe-area (`PartyMobileNav.js:16–52`); main резервирует её высоту (`PartyAppShell.js:669`, `:1013`).

Основные пункты сайдбара min-h-10 (40px), вложенные min-h-8 (32px), hamburger 40×40. Они ниже удобного ориентира 44px, **но выше минимальных 24px WCAG 2.5.8**, поэтому это не объявляется нарушением AA без проверки геометрии/исключений. Нет подтверждённого horizontal overflow основного содержимого. В desktop live sidebar NAV имел clientWidth=233, scrollWidth=234, clientHeight=641, scrollHeight=901; скриншот показал собственные полосы прокрутки. Разницу 1px не раздуваю в значимый UX-дефект.

Zoom 200%, mobile layout, длинные переводы и touch жесты B не проверяла. Полный responsive score на основании desktop/source не присваивается.

## Положительные доказательства

- Модалка имеет role=dialog, aria-modal и имя; закрытие по Escape и возврат на «+ Заказ» реально работают. Начальный фокус — именованная кнопка «Закрыть». `components/Modal.js:42–98` содержит focus trap с фильтрацией disabled/inert/невидимых контролов.
- Поля мастера используют настоящие label/select/input/textarea, а не click-only div. На шаге типа accessible name корректен; текущий progress отмечен `aria-current="step"` (`PartyOrderWizard.js:485`).
- Загрузка/ошибки снабжены role=status/alert и повтором (`PartyOrderWizard.js:1116–1128`, availability). Ошибки конкретные и на русском.
- Защита несохранённых изменений подключена (`PartyOrderWizard.js:108–116`), runtime имеет beforeunload; это предупреждение перед потерей, а не автосохранение/восстановление черновика. Не следует обещать draft recovery.
- При неоднозначном сохранении есть idempotency key, блокирование повторной редактируемой операции и «Проверить сохранение» (`:355–385`, `:400–426`); double-save guard существует. Реальные сетевые сбои не вызывались.
- При полученном авансе есть отдельный текст о фактическом получении и отдельная сущность ожиданий (`:1054–1067`); не смешивать эти действия при предложениях упрощения.
- Мобильные shortcuts строятся из уже авторизованного desktop menu (`helpers/partyMobileNavigation.js`), создание проверяет permission в активном membership, дубли удаляются. Нижние ссылки уже имеют aria-current.
- Редактор сохранённого заказа уже реализует roving tabindex, Arrow/Home/End для tablist (`PartyRoleOrdersWorkspace.js:534–599`); переносить этот положительный вывод на все шаги нового мастера нельзя.

## Browser / overlay run notes для parent

- Свежие CUA вкладки созданы B, существующие не выбирались. Первая имела локальный id 1, вторая id 2; parent предупреждён о возможной неоднозначности id между агентами. Все взаимодействия проведены через собственные handles `uxBTab`/`uxB2Tab`.
- На второй попытке create с visible:false получено: `IAB visibility is not supported in a subagent thread`. Прочитано browser-troubleshooting, новая вкладка успешно создана без этой настройки. Видимость не менялась.
- Документированная `playwright.evaluate` поверхность read-only; доступного mutable injection API нет. Устанавливать document.title или добавлять script через неё запрещено правилами инструмента, поэтому preflight/injection не обходились.
- **Надёжного пользовательского overlay нет**, console findings от injected detector нет. Live-server не запускался, инъекция detect.js не выполнялась; нечего останавливать/удалять. Fallback: настоящий source CLI detector + ручные DOM/computed-style/AX/клавиатурные доказательства + in-memory screenshot.
